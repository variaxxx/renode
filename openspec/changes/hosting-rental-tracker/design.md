## Context

В репозитории пока нет приложения, API и схемы данных. См. [proposal.md](proposal.md) для мотивации и четыре delta spec для наблюдаемого поведения. Сервис предназначен для одного владельца; браузер должен расшифровывать пароли провайдеров, а сервер должен отправлять Telegram-напоминания даже при закрытой админке.

## Goals / Non-Goals

**Goals:**
- Разделить обычные данные учета, доступные серверному воркеру, и секреты, доступные только в разблокированном браузере.
- Сделать первую версию пригодной для развертывания с PostgreSQL и резервного копирования.
- Гарантировать явное состояние отправки уведомлений и предсказуемый учет дат и валют.

**Non-Goals:**
- Сервер не входит в кабинеты провайдеров и не расшифровывает их пароли.
- Нет синхронизации с API провайдеров, командных ролей и конвертации валют по курсу.

## Decisions

### 1. Веб-приложение, интерфейс и хранилище

Frontend — TypeScript/React с Vite, Tailwind CSS и shadcn/ui. Backend API и отдельный процесс воркера — TypeScript/NestJS под Bun; Bun также управляет зависимостями и скриптами проекта с фиксированным lockfile. Использовать Prisma ORM для доступа к обычному PostgreSQL и версионированных миграций Prisma Migrate. Это не требует управляемого продукта Prisma Postgres. API и воркер подключаются к одной БД через отдельные процессы; воркер не получает ключи хранилища паролей. Секрет подключения к БД хранить вне репозитория. Для локальной разработки поднимать PostgreSQL в контейнере; в развертывании допустим отдельный контейнер с постоянным томом или управляемая БД. В первом шаге проверить запуск NestJS и Prisma Client под Bun до реализации бизнес-функций.

Для backend применять локальный skill `nestjs-feature-architecture`: группировать модули по возможностям (`owner-access`, `providers`, `servers`, `payments`, `credential-vault`, `notifications`), оставлять HTTP-контроллеры тонкими, бизнес-правила — в сервисах, Prisma-вызовы — в репозиториях, ввод и вывод — в явных DTO. Общие Prisma-клиент, конфигурацию, guards и обработку ошибок держать в инфраструктурных и общих модулях. Не добавлять отдельный слой там, где он не дает полезной границы. Установить ESLint и Prettier для frontend и backend с командами проверки; форматирование и lint выполнять после каждого небольшого этапа. Новые функции и методы снабжать короткими комментариями на английском согласно инструкциям проекта.

Тема интерфейса в первой версии фиксированная темная: применить `dark` к корню документа до отображения приложения, использовать цветовые токены shadcn/ui и не добавлять переключатель темы. Общие элементы (кнопки, формы, таблицы, диалоги и сообщения об ошибках) строить из компонентов shadcn/ui, чтобы экраны оставались согласованными. Проверять контраст и состояния фокуса в темной палитре.

Основные модели Prisma: `owner`, `session`, `provider`, `server`, `payment`, `notification_settings`, `notification_delivery`, `vault`, `provider_secret`. Добавлять модели и миграции по функциям, а не одной большой миграцией перед всей реализацией. Денежные суммы хранить в минимальных единицах или в точном decimal-представлении с кодом валюты, без чисел с плавающей точкой. Даты оплаты, окончания и отмены хранить отдельно. Архивация сохраняет историю и выключает будущие напоминания. Удаление провайдера с серверами запрещено; сервер с платежами можно только архивировать. Удаление сервера без платежей требует подтверждения и удаляет его секреты и ожидающие уведомления.

Альтернативы: desktop-приложение усложняет доставку и синхронизацию, когда весь учет нужен в вебе; SQLite проще в эксплуатации для одного владельца, но PostgreSQL выбран владельцем и дает надежные транзакции и блокировки для совместной работы API и воркера. Светлая тема и переключатель темы не входят в первую версию.

### 2. Вход владельца

Первоначальная учетная запись создается отдельной командой настройки при развертывании, без публичного маршрута регистрации. Пароль входа хранится как Argon2id-хеш. Сессия — серверная, браузер получает cookie с `HttpOnly`, `Secure` и `SameSite`; изменяющие запросы дополнительно защищены от CSRF. Ограничить попытки входа. Вход в админку не разблокирует секреты; это отдельное действие.

Альтернатива: один общий пароль для входа и расшифровки проще для пользователя, но смешивает независимые функции и повышает риск раскрытия мастер-пароля серверу.

### 3. Шифрование паролей провайдеров

Браузер создает случайный ключ данных (DEK) и шифрует каждую запись алгоритмом AES-256-GCM с новым случайным nonce. Ключ, полученный из мастер-пароля через Argon2id с индивидуальной солью, шифрует DEK. Независимый случайный резервный ключ также шифрует DEK; он показывается владельцу при создании хранилища один раз. Сервер хранит шифротексты, соли, nonce, версии формата и две зашифрованные копии DEK. Открытые пароли, мастер-пароль, резервный ключ и открытый DEK не отправляются на сервер и не сохраняются в браузерном постоянном хранилище. После закрытия вкладки хранилище снова заблокировано. Смена мастер-пароля или восстановление меняет обертку DEK, не перешифровывая каждую запись.

Пароль провайдера привязан к провайдеру; обычные заметки и поля каталога считаются нешифрованными. Интерфейс явно отделяет секретные поля от обычных. Для всего сайта обязательны HTTPS, строгая политика загрузки скриптов, отсутствие стороннего JavaScript на странице хранилища и безопасный вывод пользовательского текста.

Альтернативы: серверное шифрование дает серверу возможность расшифровать данные; хранение ключа в `localStorage` или рядом с шифротекстом лишает схему смысла. Готовый менеджер паролей был бы проще, но владелец выбрал встроенное хранение.

### 4. Напоминания и Telegram

Привязка Telegram идет через короткоживущую одноразовую ссылку `/start` из авторизованной админки; backend сохраняет chat ID только после подтверждения токена. Настройки хранят часовой пояс и интервалы по дням для каждого типа события. Воркер периодически выбирает наступившие события в локальном времени владельца, резервирует запись доставки с уникальным ключом `(server_id, event_type, event_date, interval)` и отправляет сообщение. Он сохраняет результат и повторяет временные ошибки с задержкой. При изменении даты оплаты или архивации старые события больше не подходят для отправки. Сообщения содержат название, тип события, дату и ссылку на админку, но никогда не содержат пароли или секретные заметки.

Базовое время отправки — 09:00 в часовом поясе владельца. Кнопка «Оплачено» в админке предлагает следующую дату на основе периода оплаты, но владелец подтверждает ее до сохранения. Суммы разных валют показываются раздельно.

Альтернативы: планировать отдельную задачу на каждое напоминание сложнее при изменении дат; периодический расчет из БД проще и устойчивее к перезапуску. Telegram-кнопки для изменения платежей откладываются: они требуют отдельной защиты команд и подтверждения.

## Risks / Trade-offs

- Компрометация веб-страницы во время разблокировки может раскрыть секреты → защищать доставку frontend, CSP, зависимости и вывод данных; не обещать абсолютную защиту от скомпрометированного сервера.
- Потеря мастер-пароля и резервного ключа делает пароли невосстановимыми → показывать предупреждение и проверку сохранения резервного ключа при настройке.
- Telegram может принять сообщение, а процесс упасть до записи успеха → возможна повторная отправка после сбоя; хранить ключ доставки и помечать успех сразу после ответа API.
- PostgreSQL добавляет отдельный сервис и управление подключениями → ограничить пул соединений API и воркера, следить за доступностью БД и выполнять регулярные резервные копии с проверкой восстановления.
- Bun может выявить несовместимость конкретных версий NestJS или Prisma → сначала проверить минимальный запуск API, воркера, Prisma Client и миграций под закрепленными версиями, затем строить функции поверх этого основания.
- Бэкап БД содержит открытые метаданные серверов и платежей → защищать резервные копии и доступ к серверу отдельно от шифрования паролей.

## Implementation Sequence

Реализацию вести короткими вертикальными этапами из [tasks.md](tasks.md): в одном запросе на apply выполнять только одну указанную нумерованную группу, проверять ее результат и останавливаться перед следующей группой. Простое дробление чекбоксов не ограничивает объем одного запуска apply, поэтому запрос на каждый запуск должен прямо называть границу группы. Не добавлять файлы тестов без отдельного запроса владельца; для каждого этапа использовать указанные в задачах команды сборки, lint, форматирования и ручные проверки поведения.

## Migration Plan

1. Поднять PostgreSQL, применить миграции, затем развернуть API и воркер с HTTPS и защищенным подключением к БД.
2. Через команду настройки создать единственного владельца; настроить серверный токен Telegram-бота вне репозитория.
3. Владелец входит, создает хранилище, сохраняет резервный ключ, привязывает Telegram и отправляет тестовое сообщение.
4. При откате остановить воркер перед API, создать резервную копию PostgreSQL и вернуть предыдущую версию приложения; миграции с потерей данных требуют отдельного плана отката.
